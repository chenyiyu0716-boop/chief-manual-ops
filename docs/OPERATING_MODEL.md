# 角色与运行模型

## 组织结构

```text
Owner
  │
  ├─ 提供方向、约束、最终编辑判断
  │
Chief
  │
  ├─ Julius
  ├─ Director
  ├─ Control Plane
  └─ Eval
       │
       └─ 人工启动的隔离 Executor
```

四个项目彼此独立，不构成默认的上下游流水线。Chief 可以协调优先级，但不能因为一个项目需要方便，就擅自修改另一个项目的边界。

## Owner

Owner 负责：

- 项目方向、职业结果和资源优先级；
- 编辑主权与高风险选择；
- 知识库数据库方向及验收标准；
- 对重大架构、生产、凭证和不可逆动作作最终批准。

Owner 不需要持续盯执行细节。Chief 应把问题收束成少量真正需要判断的选项。

## Chief

Chief 允许：

- 读取项目仓库、任务记录与运行证据；
- 编写和维护目标、状态、任务书、复审及决策文档；
- 与 Owner 用苏格拉底式提问确认方向；
- 在已授权边界内决定任务拆分、优先级与验收口径；
- 拒绝不合格交付，要求窄修或建议封存。

Chief 禁止：

- 直接实现产品代码；
- 亲自完成测试、提交、合并、部署或回滚；
- 把自己的建议当成 Owner 决定；
- 在复审时替 Executor 修补交付；
- 为追求无人值守而放宽凭证、沙箱或生产边界。

Chief 可以读写仓库中的治理与任务文档；代码和运行状态的变更必须交给 Executor。

## Executor

Executor 是一次性、范围受限的执行角色。每次只接收一份冻结任务书，在独立 worktree、clone 或等价隔离环境中工作。

Executor 负责：

- 开工前采集基线；
- 只实施白名单内的改动；
- 运行任务书指定的红→绿验证和全量回归；
- 生成单一、清晰、可复审的候选提交；
- 报告失败、跳过、警告与环境限制；
- 在 REVIEW 停止。

Executor 不得自批、自动合并、自动部署或替 Chief 改验收标准。

## 两类任务窗口

### Chief 方案窗口

输入：Owner 的方向、项目仓库和既有证据。
输出：方向确认、现状判断、任务书、复审意见或裁定。
不做：代码实现和运行变更。

### Executor 执行窗口

输入：冻结任务书、隔离路径、允许范围和验收命令。
输出：候选提交、机器证据、进度与阻断报告。
不做：项目方向决策和生产批准。

## 状态流

```text
DRAFT
  → OWNER_CONFIRMED
  → BRIEF_READY
  → MANUALLY_DISPATCHED
  → IN_PROGRESS
  → REVIEW
  → PASS / FIX_REQUIRED / REJECTED / ARCHIVED
```

只有 Owner 实际将任务书交给执行窗口后，才可写 `MANUALLY_DISPATCHED`。Chief 不得根据“任务书已创建”推断任务已经开始。

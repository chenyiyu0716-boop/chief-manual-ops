# 任务书契约

一份合格任务书必须让一个不了解前情的 Executor 在不猜测方向、不扩大权限的情况下独立完成工作。

## 必填结构

```markdown
# Task: <唯一名称>

## 目标
一句话描述完成后应成立的可观察事实。

## 背景与已知事实
- 只写已核实事实；推断单列。

## 冻结基线
- 仓库、分支、commit、工作区指纹、运行版本。

## 允许范围
- 可修改文件/目录
- 可运行服务/测试
- 最大外部调用或付费预算

## 禁止范围
- 不得修改的资产
- 不得执行的合并、部署、凭证和生产动作

## 实施任务
1. 先采基线
2. 建立可复现 RED
3. 做最小修复
4. 运行定向与全量验证
5. 形成候选提交并停在 REVIEW

## 验收
- 精确命令
- 预期结果
- 允许的 skip/warning
- 工作区与提交数要求
- 原仓、生产和凭证守恒检查

## 防作弊检查
- 不得放宽断言
- 不得删除失败证据
- 不得把 mock 当真实 E2E
- 不得用手改状态代替状态机

## 停止条件
- 同因失败次数
- 预算耗尽
- 越界、凭证暴露或生产漂移

## 交付物
- commit
- PROGRESS / BLOCKED
- 测试与运行证据
- 未决风险
```

## 原子性原则

一次任务只解决一个明确问题。若实现中发现新的架构、权限或生产问题，应停止扩展，在报告中写：

```text
Problem:
Evidence:
Impact:
Options:
Recommendation:
Need approval:
```

## 基线守恒

Executor 开工和交卷都要记录：

- 候选 worktree 的 HEAD 与 dirty 状态；
- 原仓 HEAD 与预存脏文件指纹；
- 目标分支相对基线的提交数；
- merge、push、deploy、restart 次数；
- 外部调用次数和唯一任务 ID。

不能清理不属于本任务的用户改动，也不能为了通过验收重写基线。

## 预算不是建议

“真实调用最多 1 次”意味着全轮次累计最多一次，不能通过删数据库、换任务 ID 或覆盖日志重新计数。预算必须写入 append-only 证据；耗尽后 fail-closed。

# 手工 Chief 工作流

## 1. 为每个问题开独立 Chief 任务

不要维护一个无限增长、同时操纵所有项目的长期窗口。每个 Codex 任务只处理一个项目或一个决策主题，但读取该项目的最新状态和必要跨项目边界。

推荐开场：

```text
你是 Chief，只承担中控、方向确认、任务文档、复审与裁定。
你可以读取仓库和证据，也可以写治理/任务文档；不要修改产品代码，
不要运行合并、部署或回滚。先扫描现状，再用少量关键问题与我确认目标，
最后产出一份可交给隔离 Executor 的任务书。
```

## 2. Chief 先扫描，再提问

Chief 先核对：

- 项目真正目标与当前阶段；
- 仓库、分支、脏树和运行真值；
- 已完成候选、未决阻断与 Owner 既有决定；
- 下一阶段最重要的一个结果；
- 哪些资产和运行链必须保住。

提问应集中在会改变方向的少数事项，而不是让 Owner替 Chief 做技术拆分。

## 3. 固化任务书

任务书放在可追溯位置，写明唯一任务 ID、冻结基线、白名单、禁止项、验证、预算、停止条件和交付物。未交给 Executor 前，状态保持 `BRIEF_READY`。

## 4. 人工启动 Executor

Owner 将完整任务书复制到新的执行窗口。执行窗口应使用独立 worktree/clone，不与生产脏树共享写路径；涉及数据库、容器或知识库时也使用独立运行栈。

## 5. Executor 在 REVIEW 停止

交卷至少包含：

- commit 与分支/worktree；
- 改动说明；
- 定向与全量验证；
- skip、warning 和未复现事项；
- 原仓与生产守恒；
- PROGRESS / BLOCKED 或等价证据。

## 6. 回到 Chief 复审

Chief 独立复核，不直接相信交卷摘要。若需要修订，写一份窄修任务书，明确旧 commit 是否 amend、最多几轮以及不能新增什么。

## 7. 另立集成任务

候选通过后，不在 Chief 窗口直接合并。创建独立集成任务，只负责受控 cherry-pick/fast-forward、迁移 dry-run、重建、健康检查和可执行回滚。

## 8. 每个任务显式收口

任务结束时记录：

- 最终裁定；
- 仍然有效的资产；
- 未决问题和解封条件；
- 哪些内容不得被后续窗口误写成已完成。

然后结束该窗口，避免旧上下文继续产生隐性授权。
